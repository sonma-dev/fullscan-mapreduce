To consider IT system migration, this experiment attempts to extract specifications from existing detailed design documents.
The design document is, of course, a synthetic sample.
While an individual cannot hold an advantage over enterprise scale, please use this as a reference.

Note that I do not claim that this method will reduce the personnel, time, or cost required for the entire development of a new system, including requirements definition, testing, etc.
Also note that normally, additions and deletions of functions for the new IT system—in other words, specification changes—should be taken into account; however, for the sake of simplicity, this experiment does not consider them.

## Objective

To generate specifications from existing detailed design documents using full load, 1-level hierarchical MapReduce, and 2-level hierarchical MapReduce approaches, and evaluate the accuracy of the generated specifications using precision, recall, and the F1 score.
Although this approach is tautological, wouldn't it help verify whether valid specifications can be generated from existing design documents?

I explicitly state that the same statistical method was used to calculate the precision, recall, and F1-score for all three methods.

## Main conclusion

- In the Full Load approach, I did not provide the LLM with input exceeding its context window. **Nevertheless, the Full Load approach yielded lower precision, recall, and F1 scores than the MapReduce approaches.**
- It is necessary to verify the validity of the experimental methods, including the source code logic and the calculation of TP, FP, TN, and FN.
- Further investigation into N-level hierarchical MapReduce is necessary before drawing definitive conclusions.
- Results also depend on how the gold set is constructed. If the gold set is exported as a separate file directly from the original document (the PDF), it is difficult to accurately measure TP, FP, TN, and FN.
- In a general N-level hierarchical MapReduce implementation, wall-clock time tends to increase with the depth of the hierarchy because each fork may require additional operations, such as aggregation and approval.
- Further experiments are needed to isolate the effects of factors such as hierarchy depth and global context at each level.
- Multiple experiments for each approach are necessary to obtain statistically significant results before claiming that MapReduce is superior.
- **Currently, global and subglobal contexts are generated by standalone LLM calls, but in the future, these tasks might be handled by dedicated agents acting as the root node and fork nodes, respectively.**
- **To mitigate Attention Dilution in AI, we could organize fork nodes into a two-level hierarchy for documents containing a large number of chapters, or extend the hierarchy to multiple levels as needed.**
- **With LLM-based MapReduce methods, pursuing semantic accuracy requires incurring high wall-clock time and input/output token costs. Conversely, pursuing high speed comes at the expense of semantic accuracy.**

Note that If I have enough time, I can also develop a dependency-graph-based MapReduce, rather than a tree-based MapReduce.

## Other Conclusions

- Although the chart shows approximately 1.76 million input tokens for the Full-load approach, the source PDF files were input separately to generate each of the seven specifications.
  Therefore, the combined token count of the PDF files and the previously generated specifications never exceeded the context window in any single run.
- Full-scan MapReduce consumes more tokens than Full Load. In other words, full-scan MapReduce has a cost disadvantage.
- 2-level hierarchical MapReduce requires a large amount of wall-clock time. Improving the program algorithm would likely reduce this wall-clock time.
- Results may change in the future as issues such as lost in the middle and context rot improve, and reasoning capabilities become more advanced.
- This experiment uses a relatively simple approach based on an LLM model alone. Using application software such as Codex or Kiro may potentially produce higher evaluation scores.
- I prepared a common atomic requirements ledger derived from the original PDF for use across all three methods. However, because ChatGPT was involved in the statistical analysis, it modified the ledger during the evaluation process.
- The improvement in precision is more likely attributable to the approval process than to MapReduce itself, that is, splitting the document and scanning it in full. In contrast, the improvement in recall appears to stem from the splitting process that scans every chunk.
- I did not add an approval process to the full-load approach because having a single LLM perform the approval could lead to the same errors being repeated. However, an approval process might be meaningful in a multi-pass full-load approach.
- We might be able to use the OpenAI Decisions API or TypeSafe AI Jev for the approval process and for calculating precision, recall, and F1-scores.

## Assumptions / Prerequisites

- The experimental programs consist of full load, 1-level hierarchical MapReduce, and 2-level hierarchical MapReduce.
- In this experiment, considering the large context length of gpt-6.1-sol, we compare PDF file full load with MapReduce, rather than comparing against RAG.
- Based on the detailed design documents, the eight documents were generated sequentially. The MapReduce approaches required multiple LLM calls for each of the first seven documents.
  1. Screen Functional Specification
  2. API Specification
  3. Data Specification
  4. Batch Functional Specification
  5. Business Rules
  6. Exception Handling Specification
  7. Process Flow Specification
  8. Architecture Decision Register

Note that the eighth document consolidates unresolved architectural decisions, specification gaps, and conflicts from the first seven specifications, requesting human decisions rather than allowing AI to make unsupported assumptions.
- Multiple specification documents exist. In all three methods, the specification documents are generated by cross-referencing one another.
  All three programs pass previously generated specification documents to the LLM as input.
- Both Full load and N-level hierarchical MapReduce can use an LLM in the final step of specification generation to eliminate duplicates. This was not done in this experiment.
- In 2-level hierarchical MapReduce, levels were assigned to chapters and sections, respectively.
- Since wall-clock time and total token consumption grow exponentially with the depth of the hierarchy, only the root node performs the approval process; level-1 fork nodes do not.
- In this experiment, the detailed design document was not converted using Microsoft Document Intelligence; it was passed directly to the LLM via the `input_file` parameter of the Responses API.
- I defined "duplicate" as redundant specifications across the 8 specification documents.
- Environment details:
  - LLM Model: gpt-6.1-sol
  - Reasoning effort: Low
  - Number of concurrent LLM executions: 8 for 1-level and 16 for 2-level
  - Infrastructure: Azure
  - Local Execution Environment: Gentoo Linux, Windows Subsystem for Linux
- Statistical evaluation details:
  - SaaS-hosted ChatGPT
  - Reasoning effort: High

Note that, considering AI agents fine-tuned by OpenAI, SaaS-hosted ChatGPT may be a superior metric calculation environment compared to Codex.
Also note that in N-level hierarchical MapReduce, the number of concurrent LLMs should be increased depending on $N$.

## Statistical Validation of the Evaluation Metrics
I verified the validity of the statistical method by applying it to the same set of multiple datasets for each of the three methods.
During this verification, when precision or recall was close to 100%, the values remained unchanged.
However, in the statistical calculations for full-load, when precision deviated substantially from 100%, the precision value varied considerably.
Although the precision and recall estimates obtained from the full-load evaluations with low reasoning effort are not reliable, I believe we can confidently conclude that neither precision nor recall reaches 100%.
