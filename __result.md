To consider IT system migration, this experiment attempts to extract specifications from existing detailed design documents.
The design document is, of course, a synthetic sample.
While an individual cannot hold an advantage over enterprise scale, please use this as a reference.

Note that I do not claim that this method will reduce the personnel, time, or cost required for the entire development of a new system, including requirements definition, testing, etc.
Also note that normally, additions and deletions of functions for the new IT system—in other words, specification changes—should be taken into account; however, for the sake of simplicity, this experiment does not consider them.

## 1. Other Conclusions

- Although the chart shows approximately 1.76 million input tokens for the Full-load approach, the source PDF files were input separately to generate each of the seven specifications.
  Therefore, the combined token count of the PDF files and the previously generated specifications never exceeded the context window in any single run.
- Full-scan MapReduce consumes more tokens than Full Load. In other words, full-scan MapReduce has a cost disadvantage.
- 2-level hierarchical MapReduce requires a large amount of wall-clock time. Improving the program algorithm would likely reduce this wall-clock time.
- Results may change in the future as issues such as loss in the middle and context rot improve, and reasoning capabilities become more advanced.
- This experiment uses a relatively simple approach based on an LLM model alone. Using application software such as Codex or Kiro may potentially produce higher evaluation scores.
- I prepared a common atomic requirements ledger derived from the original PDF for use across all three methods. However, because ChatGPT was involved in the statistical analysis, it modified the ledger during the evaluation process.
- The improvement in precision is more likely attributable to the approval step than to MapReduce itself, that is, splitting the document and scanning it in full. In contrast, the improvement in recall appears to stem from the splitting process that scans every chunk.
- I did not add an approval step to the full-load approach because having a single LLM perform the approval could lead to the same errors being repeated. However, an approval step might be meaningful in a multi-pass full-load approach.

## 2. Objective

To generate specification documents from existing detailed design documents using full load, 1-level hierarchical MapReduce, and 2-level hierarchical MapReduce, and to measure the accuracy of those specification documents using precision, recall, and F1 score.

While this approach is a tautology, does it allow us to confirm whether valid specifications can be generated from existing specifications and design documents?
Furthermore, does it provide insights for migrating from classical programming languages to modern programming languages?

## 3. Assumptions / Prerequisites

- The experimental programs consist of full load, 1-level hierarchical MapReduce, and 2-level hierarchical MapReduce.
- In this experiment, considering the large context length of gpt-sol-6.1, we compare PDF file full load with MapReduce, rather than comparing against RAG.
- Based on the detailed design documents, the following 7 specification documents were sequentially generated. A single query was sent to the LLM for the creation of each specification document:
  1. Screen Functional Specification
  2. API Specification
  3. Data Specification
  4. Batch Functional Specification
  5. Business Rules
  6. Exception Handling Specification
  7. Process Flow Specification
- Multiple specification documents exist. In all three methods, the specification documents are generated by cross-referencing one another.
  All three programs pass previously generated specification documents to the LLM as input.
- Both Full load and N-level hierarchical MapReduce can use an LLM in the final step of specification generation to eliminate duplicates. This was not done in this experiment.
- In 2-level hierarchical MapReduce, levels were assigned to chapters and sections, respectively.
- Root performs the approval process, but Level 1 fork nodes do not.
- In this experiment, the detailed design document was not converted using Microsoft Document Intelligence; it was passed directly to the LLM via the `input_file` parameter of the Responses API.
- The number of trials was one each for full load, 1-level hierarchical MapReduce, and 2-level MapReduce. I currently do not have the time to conduct multiple runs. If others need it, I might execute them.
- I defined "duplicate" as redundant specifications across the 7 specification documents.
- Environment details:
  - LLM Model: gpt-6.1-sol
  - Reasoning effort: Low
  - Number of concurrent LLM executions: 8 for 1-level and 16 for 2-level
  - Infrastructure: Azure
  - Local Execution Environment: Gentoo Linux, Windows Subsystem for Linux

Note that in N-level hierarchical MapReduce, the number of concurrent LLMs should likely be increased depending on $N$.
