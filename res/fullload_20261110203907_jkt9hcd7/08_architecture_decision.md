# 8. Architecture Decision Register

## How to Use This Document

This register consolidates unresolved decisions, proposals, conflicts and later-stage dependencies from the supplied specifications **01–07**. It does not amend those specifications.

Only the supplied Markdown bodies were reviewed. Quotations below are statements from those Markdown specifications, not independently verified quotations from the PDF. No original-source, Map or hierarchy-context inspection is claimed.

### Status and Implementation Boundaries

| Status | Meaning | Implementation boundary |
|---|---|---|
| TBD | A required definition or contract is missing. | Keep dependent implementation on hold; do not supply arbitrary defaults. |
| Needs confirmation | An incomplete, ambiguous or conflicting definition requires explicit confirmation. | Preserve confirmed invariants without selecting an unresolved alternative. |
| Unadopted proposal | An option or illustrative design exists, but no adoption is confirmed. | Do not treat the option as an approved contract. |
| Resolved | Explicit confirmed statements consistently answer the narrowly stated question. | Follow that answer within its stated scope; adjacent unresolved details remain open. |

Repeated statements, assumptions, illustrative values and later-generated proposals do not establish approval. No decision owner, deadline or approval date is supplied for the open items.

Implementation can proceed on confirmed authorization, isolation, grounding, immutable lineage, publication-gate, accessibility and replay-safety requirements. Technology selections, incomplete IDL, numerical settings, concurrency protocols and unresolved business predicates must remain on hold.
